# 音频缓存 L3 晋升问题修复报告

**日期：** 2026-03-04
**涉及文件：**
- `11. 音频缓存/XCAudioCacheManager.m`
- `9. 拦截缓存管理/XCResourceLoaderManager.h`
- `9. 拦截缓存管理/XCResourceLoaderManager.mm`

---

## 一、问题描述

用户发现 L3（永久缓存）始终为空，`cacheStatistics` 中 `L3_Complete.songCount` 长期为 0。
所有歌曲缓存均停留在 L2（临时缓存），冷启动后即便歌曲已完整播放过，也无法命中 L3。

**设计预期：**
- L1（内存分段）→ L2（临时文件）→ L3（永久文件）
- 切歌时触发 L2→L3 晋升，下次播放直接命中 L3

---

## 二、根本原因分析

### Bug 1（致命）：L2→L3 晋升永远被跳过

**调用链：**
```
playNextSong（XCMusicPlayerModel.mm）
  → saveAndFinalizeSong:expectedSize:0
      → finalizeCurrentSong   // L1→L2，正常执行
      → if (expectedSize > 0) // ← 永远 false，晋升逻辑被跳过
          confirmCompleteSong // ← 永远不被调用
```

**问题代码（XCMusicPlayerModel.mm）：**
```objc
NSInteger expectedSize = 0;  // 注释说"不知道完整文件大小"
[cacheManager saveAndFinalizeSong:currentSongId expectedSize:expectedSize];
```

**拦截代码（XCAudioCacheManager.m）：**
```objc
if (expectedSize > 0) {           // expectedSize 始终为 0，条件永不成立
    BOOL confirmed = [self confirmCompleteSong:...];
    ...
}
return XCAudioFileCacheStateTempFile;  // 永远在这里返回
```

**结果：** L3 目录始终为空，所有歌曲永远停留在 L2。

---

### Bug 2（次要）：L3 路径查询不支持目录扫描

`cachedFilePathForSongId:` 方法查询 L3 时使用精确路径匹配：
```objc
NSString *l3Path = [pathUtils cacheFilePathForSongId:songId originalURL:originalURL];
if ([fm fileExistsAtPath:l3Path]) { ... }
// 问题：originalURL 为 nil 时，默认 .mp3 扩展名
// 若文件实际为 .m4a，则命中失败
```

而 L2 查询有目录扫描兜底（遍历文件夹，匹配前缀），L3 没有。

**结果：** 冷启动后，`originalURL=nil` 且文件为非 mp3 格式（如 .m4a）时，L3 文件被漏掉，
误报未命中，导致 L2 先于 L3 命中，表面上看是"L2 优先于 L3"。

---

## 三、修复方案

### 修复 1：解除 `expectedSize=0` 对 L2→L3 晋升的封锁

**文件：** `XCAudioCacheManager.m`，`saveAndFinalizeSong:expectedSize:` 方法

**修改前：**
```objc
if (expectedSize > 0) {
    BOOL confirmed = [self confirmCompleteSong:songId expectedSize:expectedSize];
    if (confirmed) {
        return XCAudioFileCacheStateComplete;
    }
}
return XCAudioFileCacheStateTempFile;
```

**修改后：**
```objc
// 无论 expectedSize 是否为 0，都尝试 L2→L3 晋升
// confirmCompleteSong 内部会检查 L2 文件是否存在，不存在则安全返回 NO
BOOL confirmed = [self confirmCompleteSong:songId expectedSize:expectedSize];
if (confirmed) {
    return XCAudioFileCacheStateComplete;
}
return XCAudioFileCacheStateTempFile;
```

---

### 修复 2：L3 查询统一走 `persistentManager` 的目录扫描

**文件：** `XCAudioCacheManager.m`，`cachedFilePathForSongId:` 方法

**修改前：**
```objc
// 精确路径匹配，不支持任意扩展名
NSString *l3Path = [pathUtils cacheFilePathForSongId:songId originalURL:originalURL];
if ([fm fileExistsAtPath:l3Path]) {
    [self.indexManager updatePlayTimeForSongId:songId];
    return l3Path;
}
```

**修改后：**
```objc
// 通过 persistentManager，复用其目录扫描逻辑，支持任意扩展名
NSString *l3Path = [self.persistentManager cachedFilePathForSongId:songId];
if (l3Path) {
    [self.indexManager updatePlayTimeForSongId:songId];
    return l3Path;
}
```

---

### 修复 3：晋升前校验文件完整性，防止不完整歌曲进入 L3

**背景：**
修复 1 去掉了 `expectedSize > 0` 门卫后，当用户中途切歌时（仅下载了一半），
不完整的 L2 文件也会被晋升到 L3，导致下次播放时卡在中间。

**思路：**
- `XCResourceLoaderManager` 在处理 HTTP 响应时，会从 `Content-Range` 或 `Content-Length` 响应头中获取文件总大小，并缓存在 `songTotalLengthCache`（内存字典）中
- 在晋升前，将 L2 文件的实际大小与该值比较
- 若 `fileSize < totalLength`，说明下载不完整，拒绝晋升，保留在 L2 等系统自动清理

**新增接口（XCResourceLoaderManager.h）：**
```objc
/// 获取某首歌的已知文件总大小（来自 HTTP Content-Length/Content-Range 响应头）
/// @return 文件总字节数，0 表示未知
- (long long)totalLengthForSongId:(NSString *)songId;
```

**完整性校验代码（XCAudioCacheManager.m，`confirmCompleteSong` 方法）：**
```objc
// 比较 L2 文件实际大小与 HTTP Content-Length
long long totalLength = [[XCResourceLoaderManager sharedInstance] totalLengthForSongId:songId];
if (totalLength > 0) {
    NSDictionary *attrs = [fm attributesOfItemAtPath:tempPath error:nil];
    long long fileSize = [attrs[NSFileSize] longLongValue];
    if (fileSize < totalLength) {
        NSLog(@"[AudioCacheManager] Song %@ incomplete: fileSize=%lld < totalLength=%lld, keeping in L2",
              songId, fileSize, totalLength);
        return NO;
    }
}
// totalLength == 0 时无法校验（跳过，允许晋升）
```

**各场景行为：**

| 场景 | totalLength | fileSize | 结果 |
|------|-------------|----------|------|
| 完整播放后切歌 | > 0 | == totalLength | 晋升 L3 ✅ |
| 中途切歌 | > 0 | < totalLength | 留在 L2 ✅ |
| totalLength 未知 | 0 | 任意 | 晋升 L3（保守允许）|

> **说明：** `totalLength=0` 在正常播放流程中不会出现。`confirmCompleteSong` 只在 `finalizeCurrentSong`（L1→L2）成功后被调用，L1 有数据说明当前会话通过 ResourceLoader 下载过该歌曲，`totalLength` 此时应已被记录。

## 五、验证方法

1. **验证 L2→L3 晋升：**
   - 播放一首新歌直到结束（或播放大半后切歌且已完整下载）
   - 日志应出现：`[AudioCacheManager] Confirmed and moved song xxx to L3`
   - 重启应用，再次播放同一首歌
   - 日志应显示：`命中 L3 缓存`（而非 `命中 L2 缓存`）

2. **验证不完整歌曲被拦截：**
   - 播放一首新歌，仅播放数秒后立即切歌
   - 日志应出现：`Song xxx incomplete: fileSize=... < totalLength=..., keeping in L2`
   - 不应出现：`Confirmed and moved song xxx to L3`

3. **验证 L3 优先于 L2：**
   - 冷启动后播放已晋升到 L3 的歌曲
   - 日志应显示 `命中 L3 缓存`

4. **验证统计数据：**
   - 完整播放并切歌几次后，`cacheStatistics` 中 `L3_Complete.songCount` 应大于 0
