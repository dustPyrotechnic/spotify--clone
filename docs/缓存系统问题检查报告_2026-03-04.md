# 缓存系统问题检查报告

**日期：** 2026-03-04
**检查范围：** 三层音频缓存架构（L1/L2/L3）+ 拦截层
**结论：** 已修复 3 个致命 Bug；现存 6 个高严重度问题、6 个中严重度问题待修复

---

## 一、架构概述

项目音频缓存采用三层架构：

| 层级 | 类名 | 存储介质 | 职责 |
|------|------|---------|------|
| L1 | `XCMemoryCacheManager` | NSCache（内存） | 分段存储，100MB 上限，支持边下边播 |
| L2 | `XCTempCacheManager` | 临时文件（沙盒 tmp） | 写入中的不完整歌曲，7天过期自动清理 |
| L3 | `XCPersistentCacheManager` | 永久文件（沙盒 Library/Caches） | 完整歌曲，支持 LRU 清理 |
| 拦截层 | `XCResourceLoaderManager` | 内存字典 | AVAssetResourceLoader 代理，调度缓存读写 |

**晋升流程：** HTTP 响应数据 → L1 分段 → `finalizeCurrentSong` L1→L2 → `confirmCompleteSong` L2→L3

---

## 二、已修复问题回顾（2026-03-04）

以下三个 Bug 已在本日修复，详情见《音频缓存 L3 晋升问题修复报告_2026-03-04.md》。

### Bug 1（致命）：L2→L3 晋升被 `expectedSize=0` 永久封锁

**修复前：**
```objc
// XCAudioCacheManager.m
if (expectedSize > 0) {            // expectedSize 始终为 0，条件永不成立
    BOOL confirmed = [self confirmCompleteSong:...];
    ...
}
return XCAudioFileCacheStateTempFile;  // 永远在这里返回，L3 永远为空
```

**修复后：** 移除 `expectedSize > 0` 门卫，无论 expectedSize 是否为 0 都尝试 L2→L3 晋升。

---

### Bug 2（次要）：L3 路径查询不支持任意扩展名

**修复前：** 使用精确路径匹配，`originalURL=nil` 时默认 `.mp3`，漏掉 `.m4a` 等格式文件。
**修复后：** L3 查询统一走 `persistentManager.cachedFilePathForSongId:`，复用目录扫描逻辑。

---

### Bug 3（防护）：晋升前缺少文件完整性校验

**问题：** 移除 `expectedSize>0` 门卫后，中途切歌时不完整 L2 文件也会被晋升到 L3。
**修复：** 晋升前对比 L2 文件大小与 HTTP `Content-Length`，不完整则拒绝晋升。

## 三、现存高严重度问题（P1–P6）

### P1｜L1｜NSCache 自动驱逐不同步 `totalCost`

**文件：** `11. 音频缓存/L1/XCMemoryCacheManager.m`

**位置：**
- 问题根源：第 453–457 行 `cache:willEvictObject:` 回调
- 相关写入：第 129–131 行 `storeSegmentData:` 中 `self.totalCost += cost`

**问题描述：**

当系统内存压力大时，NSCache 会自动驱逐缓存对象并触发 `cache:willEvictObject:` 代理回调。当前该回调为空（注释掉了日志）：

```objc
// XCMemoryCacheManager.m:453-457
- (void)cache:(NSCache *)cache willEvictObject:(id)obj {
    // 当 NSCache 自动移除对象时调用（内存压力大时）
    // 可以在这里做日志记录，但通常不需要特别处理
    // NSLog(@"[MemoryCache] Object evicted due to memory pressure");
}
```

`_totalCost` 仅在以下情况被手动减少：
- `clearSegmentsForSongId:`（第 231 行）
- `trimCache`（第 340 行）
- `clearAllCache`（第 361 行）

NSCache 自动驱逐时，`_totalCost` **不会减少**，导致：
1. `totalCost` 统计值持续虚高
2. 外部读取 `totalCost` 时，以为内存仍然很满，提前触发不必要的 L1 清理
3. 实际内存已释放，但统计数据说"还在占用"，影响播放流畅性

**影响等级：** 高。在内存压力场景（后台运行、多 App 切换）下会持续触发错误的缓存清理，导致已缓存分段丢失，增加网络请求次数。

---

### P2｜L1｜`totalCost` 多线程并发读写无锁

**文件：** `11. 音频缓存/L1/XCMemoryCacheManager.m`

**位置：** 第 57 行（属性声明）、第 130 行（storeSegmentData:）、第 231 行（clearSegmentsForSongId:）

**问题描述：**

```objc
// 第 57 行
@property (nonatomic, assign) NSInteger totalCost;  // 跟踪总内存占用

// 第 130 行 storeSegmentData: 中（未加锁）
if (isNewSegment) {
    self.totalCost += cost;    // 直接写，无保护
}

// 第 231 行 clearSegmentsForSongId: 中（未加锁）
self.totalCost -= removedCost;
```

`syncQueue` 是 `DISPATCH_QUEUE_CONCURRENT`，上述写操作没有在 `barrier` 块中执行。当 `storeSegmentData:` 和 `clearSegmentsForSongId:` 在不同线程并发执行时，`totalCost` 的读-改-写操作会产生数据竞争，导致更新丢失。

**典型场景：** 播放当前歌曲时（持续写入分段）和切歌时（清理旧歌曲分段）并发发生，此时两个方向的修改可能相互覆盖。

**影响等级：** 高。在多歌曲并发播放/预加载场景下，`totalCost` 长期偏差会导致缓存误判。

---

### P3｜L2｜`fileHandleForWritingTempFile:` 文件描述符泄漏

**文件：** `11. 音频缓存/L2/XCTempCacheManager.m`

**位置：** 第 110–133 行（`fileHandleForWritingTempFile:` 方法）

**问题代码：**

```objc
// XCTempCacheManager.m:125-130
NSFileHandle *handle = [NSFileHandle fileHandleForWritingAtPath:filePath];
if (handle) {
    dispatch_sync(self.fileHandleQueue, ^{
        self.fileHandles[songId] = handle;    // ⚠️ 直接覆盖，旧 handle 未关闭
    });
}
```

若 `self.fileHandles[songId]` 中已存在一个旧的 `NSFileHandle`，新 handle 直接覆盖旧 handle，旧 handle 的 `closeFile` 永远不会被调用，其持有的文件描述符被泄漏。

iOS/macOS 单进程文件描述符上限约为 256（可通过 `ulimit -n` 查看）。每次播放一首新歌（调用此方法）都会泄漏一个描述符，积累后会触发 `EMFILE: Too many open files` 错误，导致后续文件操作全部失败。

**影响等级：** 高。长时间使用（播放大量歌曲）后必然触发，导致应用无法写入文件。

---

### P4｜L2｜`dealloc` 遍历 `fileHandles` 无锁

**文件：** `11. 音频缓存/L2/XCTempCacheManager.m`

**位置：** 第 39–44 行（`dealloc` 方法）

**问题代码：**

```objc
// XCTempCacheManager.m:39-44
- (void)dealloc {
    // 关闭所有打开的 fileHandle
    for (NSFileHandle *handle in self.fileHandles.allValues) {   // ⚠️ 无锁遍历
        [handle closeFile];
    }
}
```

`fileHandles` 字典由 `fileHandleQueue` 队列保护，但 `dealloc` 中直接读取 `self.fileHandles.allValues`，没有通过 `dispatch_sync(self.fileHandleQueue, ...)` 进行同步。若 `dealloc` 发生时其他线程正在 `fileHandleQueue` 上修改 `fileHandles`（如调用 `deleteTempFileForSongId:`），会产生数据竞争，可能导致 `EXC_BAD_ACCESS`。

**影响等级：** 中高。`XCTempCacheManager` 为单例，`dealloc` 极少触发，但若应用支持重建缓存管理器或单元测试中存在该场景，则会必现崩溃。

---

### P5｜L3｜文件名前缀匹配存在歧义

**文件：** `11. 音频缓存/L3/XCPersistentCacheManager.m`

**位置：** 第 169–176 行（`cachedFilePathForSongId:` 方法）

**问题代码：**

```objc
// XCPersistentCacheManager.m:169-176
NSArray *contents = [fm contentsOfDirectoryAtPath:cacheDir error:nil];
for (NSString *fileName in contents) {
    // 匹配 {songId}.xxx 格式的文件
    NSString *pattern = [NSString stringWithFormat:@"%@.", songId];
    if ([fileName hasPrefix:pattern] && ![fileName hasSuffix:@".plist"]) {
        return [cacheDir stringByAppendingPathComponent:fileName];
    }
}
```

`pattern = [songId].` 匹配任何以 `[songId].` 开头的文件名。若文件名格式包含多个点（如 `abc.extra.mp3`），且缓存目录中存在 songId 不同但前缀相同的文件，则可能返回错误文件路径。

此外，`contentsOfDirectoryAtPath:` 返回的顺序不稳定（由文件系统决定），第一个匹配的文件不一定是目标文件，在缓存目录存在文件名冲突时会返回不确定的结果。

**影响等级：** 高。返回错误的缓存文件会导致播放错误内容，且难以通过日志发现（日志显示"L3 命中"但实际是错误文件）。

---

### P6｜拦截层｜`loadingTasks` 混用 `dispatch_sync`/`dispatch_async` 删除

**文件：** `9. 拦截缓存管理/XCResourceLoaderManager.mm`

**位置：**
- 插入（同步）：第 250–252 行
- 删除（异步）：第 276、483、518–519、572–575 行

**问题描述：**

task 插入时使用 `dispatch_sync`（同步，确保完成后才继续）：

```objc
// 第 250-252 行
dispatch_sync(self.taskQueue, ^{
    self.loadingTasks[taskKey] = task;
});
```

但多个删除路径使用 `dispatch_async`（异步，不等待完成）：

```objc
// 第 276 行（Content Info + L3 命中路径）
dispatch_async(self.taskQueue, ^{ [self.loadingTasks removeObjectForKey:taskKey]; });

// 第 483 行（respondWithLocalFile: 完成后）
dispatch_async(self.taskQueue, ^{ [self.loadingTasks removeObjectForKey:taskKey]; });

// 第 518-519 行（respondWithCacheData: 完成后）
dispatch_async(self.taskQueue, ^{
    [self.loadingTasks removeObjectForKey:taskKey];
});
```

由于删除是异步的，在删除完成之前，同一个 task 可能：
1. 被 `cleanupStaleTasks`（定时清理）重复发现并再次调用 `finishLoadingWithError:`
2. 被新请求插入时发现旧 task 仍然存在，导致行为不确定

重复调用 AVFoundation 的 `finishLoading` 或 `finishLoadingWithError:` 会触发断言崩溃。

**影响等级：** 高。在快速切歌（快速发出多个加载请求）或定时清理与正常完成并发时可能触发 AVFoundation 崩溃。

## 四、现存中严重度问题（M1–M6）

| # | 层级 | 问题描述 | 文件 | 行号 |
|---|------|---------|------|------|
| M1 | 拦截层 | `parseRangeFromRequest:` 中 `long long` 强转 `NSUInteger`，文件 > 4GB 时溢出 | `XCResourceLoaderManager.mm` | 375–400 |
| M2 | 拦截层 | `Content-Range` 解析不校验合理性（如 totalLength < 0 或 < 请求 offset） | `XCResourceLoaderManager.mm` | 745–750 |
| M3 | 拦截层 | 网络请求失败后无重试机制，直接向 AVPlayer 返回错误，导致播放终止 | `XCResourceLoaderManager.mm` | 709–714 |
| M4 | L1 | `mergeAllSegmentsForSongId:` 遍历分段时无锁，并发写入可能读到残缺数据 | `XCMemoryCacheManager.m` | 371–396 |
| M5 | L3 | 目录扫描后、返回路径前文件可能被其他线程删除，调用方使用路径时文件不存在 | `XCPersistentCacheManager.m` | 162–186 |
| M6 | 拦截层 | `songTotalLengthCache` 字典持有所有播放过歌曲的 totalLength，无 LRU 或容量限制，长期运行内存增长 | `XCResourceLoaderManager.mm` | 48 |

## 五、建议修复优先级

按照影响范围和触发频率排序：

| 优先级 | 问题 | 理由 |
|--------|------|------|
| 🔴 立即修复 | P3（文件描述符泄漏） | 长时间使用必然触发，导致所有文件操作失败 |
| 🔴 立即修复 | P1（totalCost 虚高） | 内存压力场景高频触发，直接影响播放体验 |
| 🔴 立即修复 | P6（tasks 并发删除） | AVFoundation 断言崩溃，崩溃率问题 |
| 🟠 尽快修复 | P2（totalCost 无锁） | 数据竞争，随机触发，难以复现 |
| 🟠 尽快修复 | P5（L3 匹配歧义） | 返回错误内容，隐蔽 Bug |
| 🟡 计划修复 | P4（dealloc 无锁） | 单例极少 dealloc，风险低 |
| 🟡 计划修复 | M1、M2、M3 | 边界场景或大文件时触发 |
| 🟢 低优先级 | M4、M5、M6 | 影响较小或触发概率低 |

## 六、验证方法

### 验证 P1（totalCost 虚高）

1. 播放多首歌曲，填充 L1 缓存至 50MB 以上
2. 在 Instruments（Memory Profiler）中施加内存压力，或连接设备后发送内存警告（Debug → Simulate Memory Warning）
3. **预期**：`totalCost` 在 NSCache 自动驱逐后应下降
4. **当前实际**：`totalCost` 不变，日志显示 `trimCache freed: 0 bytes`

### 验证 P2（totalCost 数据竞争）

1. 使用 Xcode Thread Sanitizer（TSan）开启后运行
2. 快速连续播放多首歌曲（触发并发存储和清理）
3. **预期**：TSan 报告 `totalCost` 的数据竞争警告

### 验证 P3（文件描述符泄漏）

1. 通过 `lsof -p [PID] | grep tmp | wc -l` 监控进程打开的临时文件数
2. 播放 30 首不同歌曲
3. **当前预期**：打开文件数持续增长，不会回落
4. **修复后预期**：打开文件数维持在合理范围（≤ 当前播放歌曲数 + 少量余量）

### 验证 P4（dealloc 无锁）

1. 在单元测试中创建 `XCTempCacheManager` 实例（非单例），并发调用 `deleteTempFileForSongId:` 和手动 dealloc
2. 使用 TSan 检测是否有竞争
3. 或在 Xcode 中开启 Address Sanitizer 重复触发 dealloc 场景

### 验证 P5（L3 匹配歧义）

1. 手动在 L3 缓存目录（`Library/Caches/AudioCache/`）中放入两个文件：
   - `abc.mp3`（对应 songId="abc"）
   - `abc.extra.mp3`（非目标文件，模拟歧义）
2. 调用 `cachedFilePathForSongId:@"abc"`
3. **预期**：应仅返回 `abc.mp3`
4. **当前风险**：可能返回 `abc.extra.mp3`（取决于文件系统枚举顺序）

### 验证 P6（tasks 并发删除）

1. 开启 Thread Sanitizer
2. 快速切歌（在 2 秒内切换 5 首以上），同时确保切歌时有网络请求正在进行
3. **预期**：TSan 报告 `loadingTasks` 字典的并发访问问题
4. 或观察是否出现 AVFoundation 的 `finishLoading called multiple times` 断言崩溃日志
