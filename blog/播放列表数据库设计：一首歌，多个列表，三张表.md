# 播放列表数据库设计：一首歌，多个列表，三张表

[TOC]



## 前言

写个人播放列表功能，表面上看很简单：创建一个列表，往里加歌，完事。但当我真正坐下来设计数据结构的时候，才发现这个"简单"的功能里藏着一个经典的数据库难题——多对多关系应该怎么存？

这篇博客记录的是这个功能从第一版的单表暴力方案，演进到最终三表规范化设计的过程，以及每个设计决定背后的"为什么"



## 一、问题的起点：一首歌，可以在多个列表里

在开发个人播放列表功能之前，先把需求理清楚：

- 用户可以创建多个播放列表
- ，同一首歌，可以同时出现在多个列表里
- 每个列表有自己的歌曲顺序
- 有一个特殊的「喜爱的歌曲」列表，不能删除

最后一条先放一边，前三条合在一起，就构成了一个标准的多对多关系：一个播放列表包含多首歌，一首歌属于多个播放列表。

这种关系在关系数据库里怎么处理，是一道经典题目，但经典不代表没有坑



## 二、第一个念头：直接在歌曲里存 playlistId

最直觉的方案：在歌曲数据里加一个 `playlistId` 字段，存这首歌属于哪个列表

```
songs 表
┌──────────┬──────────┬────────────┐
│  songId  │  name    │ playlistId │
├──────────┼──────────┼────────────┤
│ song-001 │ 歌曲甲   │ list-A     │
│ song-001 │ 歌曲甲   │ list-B     │  ← 同一首歌，存了两条！
│ song-002 │ 歌曲乙   │ list-A     │
└──────────┴──────────┴────────────┘
```

这条路走不通，原因很明显：数据大量重复

同一首歌（相同的歌名、艺术家、封面、时长……）要在每个包含它的列表里各存一份，如果这首歌在 10 个列表里，就要存 10 条几乎完全一样的记录，这是对存储空间的浪费，更是对数据一致性的威胁——哪天要更新这首歌的封面 URL，要改 10 个地方

这违反了关系数据库最基本的原则：不要存可以推导出来的冗余数据



## 三、三表规范化：让关系独立存活

正确的解法是引入一张专门描述"关系"的中间表。最终的结构是这样的：

```
┌─────────────────────────────────────────────────────────────┐
│                       播放列表数据库                          │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│   ┌──────────────────┐         ┌──────────────────┐        │
│   │    playlists     │         │      songs       │        │
│   │   （播放列表表）  │         │    （歌曲表）    │        │
│   │                  │         │                  │        │
│   │ PK: albumId      │         │ PK: songId       │        │
│   │ ├ name           │         │ ├ name           │        │
│   │ ├ coverImgUrl    │         │ ├ artist         │        │
│   │ ├ songCount      │         │ ├ albumName      │        │
│   │ ├ createTime     │         │ ├ duration       │        │
│   │ ├ updateTime     │         │ └ ...            │        │
│   │ └ isFavorites    │         │                  │        │
│   └──────────────────┘         └──────────────────┘        │
│            △                           △                    │
│            │                           │                    │
│            └─────────────┬─────────────┘                   │
│                          │                                  │
│            ┌─────────────────────────┐                     │
│            │  playlist_song_relations │                     │
│            │      （关联表）          │                     │
│            │                         │                     │
│            │  playlistId ─────────────→ playlists.albumId  │
│            │  songId     ─────────────→ songs.songId       │
│            │  addedTime               │                    │
│            │  sortOrder               │                    │
│            └─────────────────────────┘                     │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

三张表，各司其职：

- **playlists**：只管播放列表本身的信息，不关心里面有什么歌
- **songs**：只管歌曲本身的信息，不关心在哪个列表里
- **playlist_song_relations**：只管谁和谁有关系，以及这个关系的附属信息（加入时间、排序）

这种设计在数据库教科书里叫做"第三范式"，但理解它不需要背任何术语，只需要记住一个原则：**让每个表只负责一件事**



## 四、关联表：不只是存两个 ID

关联表（`playlist_song_relations`）看起来只有两个字段有意义：`playlistId` 和 `songId`，但实际上它还携带了两个字段：`addedTime`（加入时间）和 `sortOrder`（排序序号）

这两个字段体现了一个重要的设计思想：**属于这段关系本身的信息，只能存在关联表里**

想想看，"这首歌是什么时候被加入这个列表的"——这个信息既不属于歌曲，也不属于播放列表，它属于"这首歌和这个列表之间的关系"，所以只能存在关联表里

同样的道理，如果未来要支持"在列表里手动拖拽排序"，排序序号也只能在关联表里存，因为同一首歌在不同列表里的顺序是完全独立的

```
关联表的数据示例：

playlistId  │  songId   │  addedTime      │  sortOrder
──────────────────────────────────────────────────────
list-A      │  song-001 │  1710000000000  │  0
list-A      │  song-002 │  1710000100000  │  0
list-B      │  song-001 │  1710001000000  │  0   ← 同一首歌，不同时间加入不同列表
list-B      │  song-003 │  1710001100000  │  0
```

这里还有一个细节：关联表没有独立的主键字段，`(playlistId, songId)` 这两个字段联合起来充当主键，天然保证了同一首歌不会被重复添加到同一个列表里



## 五、添加歌曲：三步联动

向播放列表添加一首歌，看起来简单，实际上是一次涉及三张表的联动操作：

```
用户点击「加入播放列表」
          ↓
    检查关联是否已存在？
          ↓ 不存在
  ┌───────────────────┐
  │ Step 1            │
  │ songs 表          │
  │ INSERT OR REPLACE │  ← 歌曲已存在则更新，不存在则插入
  └───────────────────┘
          ↓
  ┌───────────────────┐
  │ Step 2            │
  │ relations 表      │
  │ INSERT 关联记录   │  ← 记录 playlistId + songId + 当前时间戳
  └───────────────────┘
          ↓
  ┌───────────────────┐
  │ Step 3            │
  │ playlists 表      │
  │ UPDATE 计数和时间 │  ← 同步更新封面和 songCount
  └───────────────────┘
```

第一步用的是 `INSERT OR REPLACE`，而不是普通的 `INSERT`

这个选择是有讲究的：同一首歌可以加入多个播放列表，songs 表里只存一份数据，当第二个列表也加入这首歌时，songs 表里已经有这条记录了，`INSERT OR REPLACE` 会把它更新为最新的数据（万一歌曲信息有变化），而不是报错或忽略

第三步同步更新 playlists 表的计数，是一个空间换时间的权衡：每次查询某个列表有多少首歌，可以直接读 `songCount` 字段，不用每次都去 relations 表 COUNT，但代价是每次增删歌曲时都要多写一条 UPDATE



## 六、删除播放列表：songs 表不动

删除播放列表时，只删两张表的数据：

```
删除播放列表
     ↓
DELETE FROM relations WHERE playlistId = 'xxx'
     ↓
DELETE FROM playlists WHERE albumId = 'xxx'
     ↓
songs 表：保持不变
```

这是三表设计最优雅的地方之一，当我删掉一个播放列表，这个列表里的所有歌曲数据并不会消失，因为这些歌曲可能同时存在于其他播放列表里，如果连 songs 表一起删，其他列表就找不到这些歌了

只有那些"没有任何列表引用它"的歌曲，才是真正可以清理的孤立数据，这就是 `cleanOrphanSongs` 方法存在的意义——在批量操作后扫描 songs 表，找出没有任何关联记录的歌曲，把它们清理掉

```
孤立歌曲清理逻辑：

songs 表          relations 表
┌──────────┐      ┌───────────────────┐
│ song-001 │  ←── │ (list-A, song-001)│  ← 被引用，不删
│ song-002 │  ←── │ (list-B, song-002)│  ← 被引用，不删
│ song-003 │      │                   │  ← 没有任何引用，孤立，删除
└──────────┘      └───────────────────┘
```



## 七、查询歌曲：两步走，而不是 JOIN

从播放列表里取出歌曲列表，代码里用的不是一条 SQL JOIN 语句，而是两步分开查：

```
第一步：从 relations 表取出有序的 songId 列表
SELECT * FROM playlist_song_relations
WHERE playlistId = 'xxx'
ORDER BY addedTime ASC

第二步：对每个 songId，逐条查 songs 表
for (songId in relations) {
    SELECT * FROM songs WHERE songId = 'xxx'
}
```

熟悉 SQL 的人可能会问：为什么不写一条 JOIN 语句，一次性取出所有数据？

理由有两个：

第一，项目使用的是 WCDB 框架（微信开源的 SQLite 封装），WCDB 的 ORM 设计以单表对象映射为核心，虽然支持写原生 SQL，但框架层面对跨表 JOIN 的支持并不像单表操作那样自然，用两步查反而代码更清晰

第二，播放列表的歌曲数量通常不会很多（几十首到几百首），两步查的 N+1 问题在这个量级下几乎感知不到，性能不是瓶颈，代码可读性更重要

如果播放列表的规模达到数千首歌，或者频繁被高并发调用，才值得考虑用 JOIN 或批量 IN 查询优化



## 八、isFavorites：特殊成员的处理

「喜爱的歌曲」是一个特殊的播放列表：它永远存在、不能被删除、始终排在第一位

在数据库层面，这个特殊性通过两个机制保证：

**专属标记**：`playlists` 表里有一个 `isFavorites` 字段，这个列表的 `isFavorites = YES`，`albumId` 硬编码为字符串 `"favorites"`

**不可删除保护**：`deletePlaylist` 方法的第一件事，就是检查这个字段，如果 `isFavorites == YES`，直接返回 `NO`，拒绝执行

**首位固定**：取所有播放列表时，代码分两步查：先单独取出 `isFavorites = YES` 的列表，再取其余的列表按时间排序，最后拼接，这样「喜爱的歌曲」永远出现在结果的第一位，不受排序规则影响

```
getAllPlaylists 的查询逻辑：

Step 1: 取喜爱列表
SELECT * FROM playlists WHERE isFavorites = 1
→ [「喜爱的歌曲」]

Step 2: 取其他列表，按更新时间降序
SELECT * FROM playlists WHERE isFavorites = 0
ORDER BY updateTime DESC
→ [列表B, 列表A, 列表C, ...]

Step 3: 拼接
→ [「喜爱的歌曲」, 列表B, 列表A, 列表C, ...]
```

这个处理方式把"业务规则"（喜爱列表始终在第一位）直接编码进了数据层，而不是丢给 UI 层去判断，好处是任何地方查播放列表，得到的顺序永远是一致的



## 九、songCount：主动维护的冗余字段

`playlists` 表里有一个 `songCount` 字段，这是一个有意引入的冗余字段

按照严格的数据库范式，`songCount` 完全可以通过查询计算：

```sql
SELECT COUNT(*) FROM playlist_song_relations WHERE playlistId = 'xxx'
```

但这意味着每次在 UI 上显示"这个列表有几首歌"，都要发起一次 COUNT 查询，在列表页面上同时渲染多个播放列表的卡片时，这就变成了多次 COUNT，开销是不必要的

`songCount` 作为冗余字段，代价是每次增删歌曲时要多一次 UPDATE 来保持同步，收益是查播放列表时不再需要额外的 COUNT 操作，用一次写的代价换取了多次读的简化，在读多写少的场景下是合理的权衡

同理，`coverImgUrl` 也是一个冗余字段——它记录的是列表里第一首歌的封面，用来在列表卡片上展示，而不是每次都去查关联表找第一首歌再取封面



## 十、设计的优缺点

整理一下这套三表设计在实践中的体感：

**优点**

数据零冗余，同一首歌无论加入多少个列表，songs 表始终只有一条记录，增删改都不会出现"改了一处，漏改其他地方"的问题

关系清晰，每张表的职责是单一的，读代码时知道"歌曲的信息去 songs 表找，列表里有哪些歌去 relations 表找"，不会产生歧义

扩展性好，如果未来要给列表内的歌曲加"备注"或"标签"这样的附加信息，直接在 relations 表加字段即可，不影响 songs 和 playlists 两张表

**缺点**

查询变复杂，取一个列表的歌曲，至少要两步操作，而不是一条 SELECT，代码量更多，出错的可能性也更多

计数字段需要手动维护，`songCount` 是冗余字段，必须在每次增删歌曲时同步更新，如果哪里漏掉了这次 UPDATE，显示的计数就会错误，这种"隐式约定"在多人协作的项目里容易出 bug

孤立数据需要主动清理，songs 表里可能存在没有任何列表引用的孤立记录，需要定期调用清理方法，这个操作如果忘了，数据库会慢慢积累无用数据

这些缺点在当前项目的规模下是完全可以接受的，如果是需要支持大量并发写入的服务端场景，才需要更认真地对待这些问题



## 写在最后

数据库设计的很多决定，不是非对即错，而是在不同约束下的权衡

`songCount` 要不要冗余？取决于读写比例

要不要用 JOIN？取决于框架是否友好，以及数据量是否触及瓶颈

孤立数据要不要实时清理？取决于数据量增长速度和清理的代价

这些问题的答案不是从教科书里查来的，是在写代码、遇到问题、改代码的循环里逐渐清晰的

和缓存系统那篇一样，这里也没有大量贴代码，代码是 AI 最不需要你帮它写的东西，但为什么要这么设计、每个决定背后取舍了什么——这是 AI 给不了的答案，只能自己想
