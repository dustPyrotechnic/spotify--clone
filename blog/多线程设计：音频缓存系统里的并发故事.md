# 多线程设计：音频缓存系统里的并发故事

[TOC]



## 前言

写完音频缓存系统的三层架构之后，我意识到有一个话题一直被我藏在水面下，没有讲清楚：**这套系统是怎么处理并发的**

缓存系统天然是一个多线程重灾区：AVPlayer 在后台线程请求数据，网络回调从不知道哪个线程打回来，UI 在主线程等着渲染进度，预加载在另一个线程默默下载……这些事情同时发生，任何一处没保护好，轻则数据错乱，重则直接崩溃

这篇博客不是一份"什么是 GCD"的入门教程，而是从实际问题出发，讲清楚这套系统里的每一个并发决定是怎么做的，以及为什么这么做



## 一、多线程的根源：谁在同时读写

在动手处理多线程之前，先把问题说清楚：系统里谁可能在同时访问同一份数据？

大概是这样的情况：

```
线程 A（AVPlayer 资源加载线程）
    └── 请求分段数据 → 读 L1 内存缓存

线程 B（网络回调线程，来自 AFNetworking）
    └── 下载完一个分段 → 写 L1 内存缓存

线程 C（预加载线程）
    └── 静默下载下一首歌 → 写 L1 内存缓存

线程 D（主线程）
    └── 用户切歌 → 触发 L1→L2 流转，读全量 L1 数据
```

同一份 L1 缓存数据，有线程在读，有线程在写，有线程在整体读出来转存，全部同时发生，这就是需要处理的并发问题



## 二、工具箱：GCD 和 NSLock

这套系统里用到的并发工具不多，但每种都有它明确的适用场景，先把工具和用途对应起来：

```
dispatch_queue_create（串行队列）
    → 把所有操作排队，同一时刻只有一个在跑
    → 用于文件 I/O，因为文件不能同时写

dispatch_queue_create（并发队列）+ dispatch_barrier_async（栅栏）
    → 多个读操作可以同时跑，写操作独占
    → 用于高频读的内存缓存

NSLock（互斥锁）
    → 访问前加锁，访问后解锁，同一时刻只有一个持有者
    → 用于预加载的任务队列管理

dispatch_semaphore（信号量）
    → 等待某件事情发生再继续
    → 用于测试代码里等待异步操作完成

dispatch_group（任务组）
    → 等待一批并发任务全部完成
    → 用于并发测试验证
```

每个工具都是为了解决具体问题而选择的，这一点会在后面逐层展开



## 三、L1 内存缓存：多读单写

L1 是访问最频繁的地方，AVPlayer 每次需要数据都来这里查，网络下载每收到一段数据也写到这里，这里的并发策略需要**尽量让读操作不互相等待**，同时**确保写操作独占**

选择的方案是：**并发队列 + 栅栏（Barrier）**

```
并发队列的工作方式：

正常情况（多个读操作）：
线程 A 读 ─────────────────────→
线程 B 读    ────────────────────→   // 同时跑，互不等待
线程 C 读         ───────────────→

写操作来了（栅栏）：
线程 A 读 ──────┐
线程 B 读    ───┘  等待 A/B 完成
                  ↓
              写操作 ─────→         // 独占执行
                            ↓
              后续读操作恢复并发
```

读操作用 `dispatch_sync`，调用方会等结果，但多个读者可以同时进入，互不阻塞

写操作用 `dispatch_barrier_async`，它会等待队列里所有已经进入的读操作完成，然后独占执行，写完之后后续的读才能继续

这个模式有个专门的名字叫做"读写锁"（Reader-Writer Lock），是处理高频读低频写场景的标准方案

L1 里还有一个额外的复杂性：内存警告，当系统发出内存紧张通知时，需要清理 L1 里优先级较低的数据，这个清理操作也通过栅栏写入，保证清理时没有其他读写在干扰



## 四、L2 和 L3：串行 I/O 队列

磁盘文件操作和内存不同，一个文件同时被两个线程写，结果不是谁快谁赢，而是文件内容直接损坏

L2 和 L3 的策略是串行队列：所有文件操作进同一个队列排队，同一时刻只有一个在跑

```
串行队列的工作方式：

操作 1（写文件 A）──→
操作 2（读文件 A）         ──→   // 等操作 1 完成才开始
操作 3（移动文件 A 到 L3）             ──→   // 等操作 2 完成才开始
```

L2 有两个串行队列，而不是一个，这也是一个值得说明的选择：

```
ioQueue（I/O 队列）
    → 处理文件的读写、创建、删除

fileHandleQueue（文件句柄队列）
    → 管理正在打开的文件句柄
```

分成两个的原因是：文件句柄的打开和关闭，与数据的读写，有时候需要在不同调用点上分别执行，如果用同一个串行队列，可能会出现"想在 A 的 block 里等待 B 的 block 完成"，而 B 还在队列里排着的死锁情况，分离之后，两个队列互不依赖，可以安全嵌套

L3 的索引文件比较特殊：它的写操作用的是 `dispatch_async`（异步），而不是 `dispatch_sync`（同步），也就是说，更新索引之后，调用方不会等写完再继续，这是有意的——索引保存只是"尽力而为"，即使写慢了一点，也不影响当前播放，用异步换来了不阻塞调用线程的好处



## 五、预加载队列：NSLock 的选择

预加载管理器（`XCPreloadManager`）里的并发选择和前面几层不同，用的是 `NSLock`

这里有必要解释一下为什么不继续用 GCD 队列

预加载管理器维护着一个任务队列，里面存着待预加载的歌曲、每个任务的优先级、当前正在执行的任务数等状态，对这个队列的操作包括：

- 添加任务
- 取消任务
- 查询某个任务的状态
- 调整任务优先级
- 从队列里取出下一个该执行的任务

这些操作之间有复杂的依赖关系，比如"取消一个任务"之后需要立刻启动下一个任务，两件事必须原子完成，如果中间有其他线程插进来，状态就乱了

用 GCD 队列的栅栏操作也能实现互斥，但在需要"在锁内做多件事，这些事情还可能调用其他方法"的场景下，NSLock 的代码逻辑更直观：加锁 → 做事 → 解锁，边界清晰

```
NSLock 的使用方式（简化）：

取下一个任务：
[self.queueLock lock];
    task = [self.taskQueue firstObject];
    [self.taskQueue removeObject:task];
    self.activeTaskCount++;
[self.queueLock unlock];

任务完成后：
[self.queueLock lock];
    self.activeTaskCount--;
    [self startNextTaskIfPossible];   // 在锁内调用
[self.queueLock unlock];
```

这里有一个需要特别小心的地方：**持有锁的时候不能调用可能阻塞的代码**，否则会死锁，在 `XCPreloadManager` 里，所有在锁内执行的代码都只做状态读写，真正的网络请求总是在解锁之后才发起



## 六、回调线程管理：一个容易忽略的细节

缓存系统对外暴露了很多回调（completionBlock、progressBlock），这些回调会被调用者拿去更新 UI，更新 UI 的代码必须在主线程执行，这是 iOS 的铁律

问题是：这些回调是从什么线程触发的？

网络下载完成的回调，来自 AFNetworking 的后台线程，文件写完的回调，来自各个 I/O 队列的线程，都不是主线程

如果直接在这些地方回调，调用方的 UI 更新代码就在后台线程执行，轻则行为异常，重则直接崩溃

解决方案：**所有对外的回调，显式切回主线程再触发**

```
网络回调触发点（后台线程）：
    ↓
dispatch_async(dispatch_get_main_queue(), ^{
    if (completionBlock) {
        completionBlock(songId, YES, nil);
    }
});
    ↓
调用方的 completionBlock 在主线程执行
```

这一行 `dispatch_async(main_queue)` 看起来平平无奇，但它是整个回调体系线程安全的最后一道门



## 七、测试里的多线程

代码写完，怎么验证线程安全？光靠肉眼审查是不够的

测试代码里用了两种工具来模拟真实的并发场景：

**dispatch_group（任务组）**：同时启动 100 个并发写操作，等全部完成后，验证每个数据都完整地写进去了，没有覆盖、没有丢失，这是模拟"网络高速下载，100 个分段几乎同时写入 L1"的场景

**dispatch_semaphore（信号量）**：预加载是异步的，发起请求之后函数就返回了，测试代码用信号量把异步变成同步：发起预加载 → 等待信号 → completionBlock 里发信号 → 测试继续往下跑，验证结果

```
信号量的等待模式：

dispatch_semaphore_t sem = dispatch_semaphore_create(0);

// 发起异步操作
[manager preloadSong:songId completionBlock:^(...) {
    dispatch_semaphore_signal(sem);   // 发出信号
}];

// 等待（最多 10 秒）
dispatch_semaphore_wait(sem, dispatch_time(DISPATCH_TIME_NOW, 10 * NSEC_PER_SEC));

// 到这里，异步操作已完成，可以检查结果
```

有了这些测试，"线程安全"就从一个无法证伪的断言，变成了可以每次跑的验证



## 八、整体的并发策略图

把各层的策略汇总在一起：

```
┌─────────────────────────────────────────────────────────────┐
│                     并发策略总览                             │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  L1 内存缓存         并发队列 + 栅栏                        │
│                      读：多线程并发                          │
│                      写：独占（等待所有读完成）              │
│                                                             │
│  L2 临时文件         两个串行队列                            │
│                      ioQueue：所有文件读写顺序执行           │
│                      fileHandleQueue：句柄管理独立           │
│                                                             │
│  L3 永久文件         串行队列                                │
│                      所有文件操作顺序执行                    │
│                                                             │
│  L3 索引             串行队列（异步写）                      │
│                      不阻塞调用方，尽力持久化                │
│                                                             │
│  预加载管理          NSLock                                  │
│                      复杂状态管理，多步原子操作              │
│                                                             │
│  URL 映射表          并发队列 + 栅栏                        │
│                      读多写少，同 L1 策略                    │
│                                                             │
│  对外回调            全部切回主线程                          │
│                      dispatch_async(main_queue)             │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```



## 九、几个设计取舍

**串行队列的文件操作，用的是 dispatch_sync（同步）还是 dispatch_async（异步）？**

L2 和 L3 的文件读写，大多用 `dispatch_sync`，也就是调用方会等操作完成再继续，这看起来像是在阻塞线程，但实际上调用方本身就在后台队列（比如网络回调线程），不是主线程，同步等待文件写完，是为了让上层逻辑知道"这一步完成了"，可以安全进行下一步

如果改成 `dispatch_async`，文件可能还没写完，上层就继续往下走，比如把一个还没写完的文件从 L2 移到 L3，结果就是文件不完整

L3 索引的写是个例外，它用异步，因为索引只是辅助信息，写慢了不影响播放，这是一个有意识的取舍

**NSLock 会不会成为瓶颈？**

预加载的任务调度频率不高，通常是用户切歌时才触发，不存在高并发调度的场景，NSLock 的开销在这里完全不是问题，串行队列或者栅栏操作对这个场景是过度设计

**为什么不用 Swift Concurrency（async/await）？**

整个项目是 Objective-C，当时选择是直接用 GCD，与语言一致。Swift 的 async/await 是更现代的方案，actor 模型能更优雅地解决共享状态问题，但在 Objective-C 里，GCD + 锁 是成熟且可靠的选择



## 写在最后

多线程代码有一个很有趣的特点：大多数时候它跑起来是正确的，只有在某些特定的时序下才会出错，而这种时序在测试环境里很难复现，一旦上线，错误就在用户那里随机出现

这也是为什么在写这套系统的时候，每引入一个共享状态，就要立刻想清楚：谁会读它？谁会写它？写的时候读者能不能等？

多线程设计最难的不是选工具，选 NSLock 还是串行队列，对于有经验的人来说并不难判断，难的是在开始写之前，把"什么是共享的、共享的边界在哪里"想清楚，这个思考过程，AI 帮不了多少
