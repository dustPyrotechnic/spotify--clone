# 音频缓存系统设计：从零开始到三层架构

[TOC]



## 前言

寒假项目中，遇到了缓存系统的需求，在与ai 斗智斗勇，并翻遍了网络上能找到的所有资料后，设计的一个比较完善的缓存系统，得益于苹果`AVPlayer` 自己的缓存机制为黑箱，并且`AVAssetResourceLoader` 代理机制极致复杂，从缓存系统对接`AVPlayer` 的操作也会讲解



## 一、问题的起点：音频播放为什么需要缓存？

在开发音乐播放器时，最朴素的做法是：用户点击播放 → 拿到 `URL` → 交给 `AVPlayer`，这条路径简单、直接，短期内完全可以工作，苹果的`AVplayer` 有优秀的自缓存机制，直接输入网络url 也能达到流畅播放的效果

但随着开发深入，几个问题逐渐暴露：

1. **重复流量**：同一首歌每次播放都重新请求网络，既浪费流量，又依赖网络质量
2. **切歌延迟**：下一首歌没有提前准备，每次切歌都要等待网络响应
3. **离线场景**：用户在无网环境下完全无法播放任何内容
4. **进度跳转卡顿**：拖动进度条时，如果 `AVPlayer` 需要重新发起 Range 请求，体验极差



这些问题加在一起，促使我决定建立一套系统性的音频缓存方案



## 二、第一个版本：全量内存缓存（`XCMusicMemoryCache`）

最初的设计思路非常直接：把音频文件下载下来，放进内存，播放时检测是否有缓存，若有缓存，则从内存中把数据交给`AVPlayer`。没有缓存，则直接把网络`URL`直接交给 AVPlayer，让AVPlayer 自己去播放

### 设计方案

核心容器选用了苹果原生的 `NSCache`，`NSCache` 的好处是：它内置了基于"成本"（cost）的 LRU 淘汰机制，当内存压力较大时，系统会自动清理优先级较低的对象，不需要开发者手动管理



整个流程是：

```
下载完整音频文件
      ↓
存入 NSCache（以 songId 为 key，NSData 为 value，文件大小为 cost）
      ↓
将数据写入 /tmp/MusicCache/{songId}.mp3 临时文件
      ↓
返回 file:// 路径给 AVPlayer 播放
```



配置上我们设置了两道限制：

- **单首歌曲上限**：20MB（超过则拒绝缓存，避免单首歌占满内存）
- **总缓存上限**：100MB，最多 10 首歌曲

同时监听了 `UIApplicationDidReceiveMemoryWarningNotification`，理论上可以在内存紧张时介入清理

### 这个方案的问题

表面上看，这套设计是合理的，但在实际使用中，它存在一个根本性的架构矛盾：

**它不支持流式播放（Streaming）**

全量内存缓存的前提是：**必须先下载完整的音频文件，才能开始播放**，这意味着：

- 用户点击播放后，需要等待整首歌下载完毕（对于 5MB 以上的歌曲，在普通网络下要等数秒）
- 一首歌只听了 30 秒就切走，之前下载的数据全部浪费
- 如果用户直接拖到 80% 处播放，我们也必须把前 80% 的数据全部下载
- 无法支持"边下边播"这个用户最基础的期望

此外，还有一个隐患：`NSCache` 的 `totalCostLimit` 在系统内存压力下可能被忽略，统计接口（`currentCacheSize`、`cachedSongCount`）在当时也未实现，整个方案对自身状态缺乏可观测性

同时，大批量使用内存来保存歌曲，虽然对当前的设备来说，可分配的内存都比较多，但是还是过于多了，可能会导致软件被操作系统杀死

**结论**：这套方案作为技术验证是有价值的，但它的核心模型是"预下载"而非"流式加载"，与音乐播放器的用户体验期望根本冲突，需要一套完全不同的架构



## 三、关键突破：拦截 AVPlayer 的资源请求

由于AVPlayer 自己的缓存是无法重复利用的，并且由自己来管理

要实现真正的边下边播，核心问题是：如何在不改变 AVPlayer 使用方式的前提下，插入一个自定义的数据来源？

答案：`AVAssetResourceLoaderDelegate`



### 拦截原理

`AVPlayer` 在加载资源时，会根据 URL 的 scheme 判断如何处理，对于 `http://` 和 `https://`，它会自己发起网络请求，但如果 URL 的 scheme 是它不认识的自定义 scheme，它就会转而询问 `AVAssetResourceLoader` 的代理：bro，这个 URL 的数据你来提供，我等着

我们利用了这个机制，在把 URL 传给 `AVPlayer` 之前，做一次转换：

```
原始 URL:  https://music-cdn.example.com/song.mp3?songId=12345
转换后:    streaming://12345?url=https%3A%2F%2Fmusic-cdn.example.com%2Fsong.mp3
```

自定义 scheme `streaming://` 让 AVPlayer 无法自行处理，于是所有数据请求都落到我们的 `XCResourceLoaderManager` 里，从这个时刻起，我们完全掌控了 AVPlayer 请求什么、我们返回什么



这个设计有一个精妙之处：URL 里同时携带了 `songId`（在 host 部分）和原始 URL（在 query 参数里），这样每次收到请求时，我们能同时知道要取哪首歌的缓存，以及在缓存未命中时去哪里下载原始数据



### 饿汉式单例的选择

为什么我的`XCResourceLoaderManager`选择采用了饿汉式单例模式而不是懒汉式呢？（绝对不是因为我手头有饿汉式代码的代码块可以直接复制）

`XCResourceLoaderManager` 被设计为单例，但这里选用了**饿汉式**（在 `+load` 方法中提前初始化）而非常见的 `dispatch_once` 懒汉式

原因很实际：`AVAssetResourceLoader` 要求在 AVPlayer 创建时就设置好 delegate，如果用懒汉式，第一次访问发生在主线程，而主线程可能正在处理 AVPlayer 初始化，存在竞争风险，饿汉式在 App 启动时的类加载阶段就完成了初始化，彻底规避了这个问题



## 四、三层缓存架构的诞生

拦截机制解决了"怎么接管数据流"的问题，但接下来的问题是：接管之后，数据从哪里来？怎么管理？

我设计了三个层级，每层有清晰的职责边界

```
┌─────────────────────────────────────────────────────┐
│                   播放请求进入                        │
└─────────────────────┬───────────────────────────────┘
                      │
              ┌───────▼────────┐
              │   L3 命中？    │ ─── 是 ──→ 直接从磁盘文件返回
              └───────┬────────┘
                    否↓
              ┌───────▼────────┐
              │   L1 命中？    │ ─── 是 ──→ 从内存分段组装返回
              └───────┬────────┘
                    否↓
              ┌───────▼────────┐
              │  发起网络请求  │
              │  数据→写入 L1  │
              └───────┬────────┘
                      │
          ┌───────────▼────────────┐
          │      切歌触发流转      	│
          │    L1 → L2 临时文件  	│
          └───────────┬────────────┘
                      │
          ┌───────────▼────────────┐
          │    验证完整性           │
          │    L2 → L3 永久缓存     │
          └────────────────────────┘
```

这里的设计只是一种，当然可以并且应该有比这种设计更加优秀的设计



### L1：内存分段缓存（`XCMemoryCacheManager`）

L1 是整个系统的"热数据层"，负责支撑实时播放

**核心设计：分段（Segment）**

我们没有把一首歌的数据作为一个整体存储，而是把它切成了固定大小（512KB）的分段，每个分段有自己的索引，存储时 key 格式为 `{songId}_{segmentIndex}`

分段大小 512KB 是经过权衡的：
- 太小（如 64KB）：分段数量过多，内存碎片严重，查找开销大
- 太大（如 4MB）：第一个分段要等待较长时间才能开始播放，不适合边下边播
- 512KB 在常见的 4-8Mbps 码率下，大约对应 1 秒音频，既能快速开始播放，又不会太碎

**优先级管理**

当前正在播放的歌曲，其分段拥有最高优先级，内存紧张时，系统会优先保留当前播放曲目的数据，避免播放中断

**分段合并**

L1 除了存储功能，还提供了两种合并接口：一种是内存合并（返回一个完整的 NSData），适合小文件；另一种是流式合并写入文件（使用 NSFileHandle 追加写入），内存中同时只保留一个 512KB 的分段，适合大文件，这个合并功能是 L1→L2 流转的基础

### L2：临时文件缓存（`XCTempCacheManager`）

L2 存储的是"可能不完整"的歌曲文件，位于系统临时目录 `/tmp/MusicTemp/`，文件后缀为 `.tmp`

**它的使命是承接 L1 的溢出**

当用户切到下一首歌时，上一首歌还下载了一半的数据不应该白白丢弃，切歌时，系统会把上一首歌在 L1 中的所有分段合并写入 L2，形成一个临时文件保存下来，如果下次再播放这首歌，可以从 L2 恢复，而不必重新下载已经下载过的部分

**完整性验证**

L2 的文件是"可能不完整"的，只有当文件大小与服务器返回的 `Content-Length` 完全一致时，才认为下载完整，然后将文件从 L2 移动到 L3，这个"验证后移动"的机制，保证了 L3 里永远只有完整的文件

**过期清理**

临时文件有 7 天过期时间，超过 7 天的临时文件会被定期清理，防止占用过多磁盘空间（L2 上限设为 500MB）

### L3：持久化完整缓存（`XCPersistentCacheManager` + `XCCacheIndexManager`）

L3 是"冷数据层"，存储在 `Library/Caches/MusicCache/`，里面只有**验证完整的**歌曲文件，这些文件在 App 重启后依然存在，是真正意义上的离线缓存

**双组件设计**

L3 由两个组件协同工作：

- `XCPersistentCacheManager`：负责文件本身的读写、移动、删除
- `XCCacheIndexManager`：负责维护一个 index.plist 索引，记录每首歌的元数据（文件大小、缓存时间、最后播放时间等）

两者分离的好处是：文件操作和元数据管理各司其职，代码边界清晰，且索引的读写开销远小于文件操作

**LRU 淘汰**

L3 的容量上限是 1GB，每次从 L3 播放歌曲时，会更新该歌曲在索引中的"最后播放时间"，当总大小超过 1GB 时，会按照最后播放时间从远到近排序，优先删除最久未播放的歌曲，直到总大小回到限制以内





## 五、统一：`XCAudioCacheManager`

有了三层缓存，还需要一个统一的入口，`XCAudioCacheManager` 扮演了这个角色——它是所有外部代码与缓存系统交互的唯一接口



调用者不需要知道"这首歌在 L1 还是 L3"，只需要问：「这首歌有缓存吗？给我一个可以播放的路径」，`XCAudioCacheManager` 内部会按照 L3 → L1 的顺序查找，找到就返回，找不到返回 nil



同样，切歌时的 L1→L2 流转、完整后的 L2→L3 移动，也都通过 `XCAudioCacheManager` 对外暴露，而不是让调用方直接操作各层管理器

这种"门面"设计有一个重要的工程价值：未来任何缓存层的内部实现变化，都不会影响外部调用代码

简单来说，就是解耦合



## 六、深入拦截器：细细细细细细

`XCResourceLoaderManager` 是整个系统最复杂的部分，因为它要直接面对 `AVPlayer` 的各种请求，稍有不慎就会导致播放失败

### Content Info 探测请求

AVPlayer 在真正请求数据之前，会先发一个"探测请求"：Range `bytes=0-1`，目的是获取文件的总长度和格式信息（Content-Type）

这个探测请求必须特殊处理：只能返回元数据（contentInformationRequest），不能调用`respondWithData`，如果把 2 字节的数据也一并返回，AVPlayer 会认为文件就是 2 字节，后续的解码会彻底失败



处理逻辑是：检测到 `loadingRequest.contentInformationRequest != nil` 时，标记为探测请求，完成后只调用 `finishLoading`，不传任何数据

### 总长度的维护问题

当 L1 命中时，我们手头只有部分数据（某几个 512KB 分段），但 `contentInformationRequest.contentLength` 必须填写文件的**总长度**，而不是已缓存的数据大小

如果填错了（比如填成了缓存数据的大小），AVPlayer 会认为文件就这么长，播放到那里就停止，不会再请求后续数据——这就是音频被截断的根本原因

解决方案是维护一个 `songTotalLengthCache` 字典：每次从网络收到响应时，从 `Content-Range` 头解析出文件真实总长度，并记录下来，L1 命中时，优先使用这个字典里的值来填充 contentLength



### 分段有效性检查

网络异常有时会导致写入的分段数据不完整（比如只有几十字节），一个小于 1KB 的分段几乎可以断定是损坏数据，在从 L1 组装数据时，如果发现任意分段小于 1KB，会认为缓存无效，清理掉该歌曲的所有 L1 分段，重新发起网络请求



### Range 请求的解析优先级

AVPlayer 描述"我需要哪个范围的数据"有两种方式：一是通过 `AVAssetResourceLoadingDataRequest` 的属性，二是通过原始 HTTP 头的 `Range` 字段，这两者有时会不一致

我们的策略是：优先使用 `dataRequest` 的属性（这是 AVPlayer 的真实意图），仅在 `dataRequest` 不可用时才解析 HTTP Range 头作为兜底



### MIME Type 与 UTI 的转换

AVPlayer 的 `contentInformationRequest.contentType` 期望接收的是 UTI（统一类型标识符），格式如 `public.mp3`，而不是通常的 MIME 类型 `audio/mpeg`，如果直接填入 MIME 类型，部分格式（尤其是 M4A/AAC）会导致播放器初始化失败

因此在填充 contentType 时，需要做一次映射转换

如果保证格式没有问题的话，也可以忽略这一步



### 首次请求的缓存阈值

当 AVPlayer 请求从文件开头（offset = 0）开始的数据时，L1 必须有足够的数据才能使用，如果缓存里只有第一个 512KB 分段，但 AVPlayer 要求从头到尾，那这个缓存是不够用的

设计上，首次请求（offset = 0）要求 L1 至少有一个完整分段（512KB）才会尝试使用缓存；而非首次请求（进度条拖动到中间某处），只要对应分段存在就直接返回





## 七、预加载系统：主动出击

被动的"播放时再缓存"终究只是减少了重复请求，但没有消除等待，要真正做到"点击即播"，需要主动预加载

`XCPreloadManager` 实现了一个带优先级的预加载队列：

预加载使用枚举值来判断是否为优先值



- **高优先级**：下一首歌（用户最可能马上要听的）
- **普通优先级**：当前播放列表中的其他歌曲
- **低优先级**：后台静默缓存
- 

预加载的目标不是把整首歌下载完，而是**只下载前几个分段**（可配置，默认只预载到 L1），对于码率 320kbps 的歌曲，512KB × 3 段 ≈ 1.5MB，大约对应 3-4 秒的播放时间，只要用户点击播放时这几个分段已经在 L1 里，就可以实现几乎零延迟的开始播放

并发数默认为 1，避免多首歌同时下载抢占带宽影响当前播放的歌曲，当用户切歌时，会自动调整优先级：把新的下一首提升为高优先级，同时取消已无意义的低优先级任务



## 八、设计回顾

回头看这段设计演进，有几个值得记录的思维转变：

第一版 `XCMusicMemoryCache` 把一首歌视为一个不可分割的整体，这个假设在"全部下载完再播放"的场景下是合理的，但一旦要支持流式播放，这个假设就崩塌了，切换到分段模型之后，流式播放、断点续下、进度跳转才真正变得可实现

第一版把控制权交给了 AVPlayer，缓存只是一个旁路，第二版通过拦截机制，把控制权收回到应用层：AVPlayer 发出请求，我们决定数据从哪里来，这个控制权的转移是整个架构升级的基础

内存快但易失，磁盘慢但持久，三层设计让不同生命周期的数据住在最合适的地方：热数据在内存（L1），待确认的数据在临时磁盘（L2），冷数据在永久磁盘（L3），数据会随着确认程度自动在层级间流转，不需要调用方关心
